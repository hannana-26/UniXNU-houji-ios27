# 内存轮(r74)第 0 步:设计定案(2026-11-27,零上机零代码,全文=本文;批准后实施)

证据分类:**实锤**=当场读到的文件原文+行号;**推测**=无日志佐证;**未确认**=没查到。
背景:固定顺序文件 `修复顺序重议_性价比版_2026-11-27.md` §十(用户 2026-11-27 11:15 批准)=多核(r73 已收线)→**内存(r74,本文)**→调频→GPU。

## 一、目标与上限(实锤)
把 XNU 可用内存从 2 GiB 扩到 **8 GiB**(本轮上限,理由三条):
1. **解析器硬上限**:`drivers/DarwinBoot/DarwinBootPkg/Driver/WindowSize.h:7` `size <= 0x200000000ULL`=8 GiB(还要 2MB 对齐,8GiB 满足)。
2. **先例天花板**:lonzzi(r35"8 GiB window"装载测试通过,同机)、nian0114(8 GiB 系统配置)、liimagination(8 GiB 物理进桌面)——三家全是 8 GiB 量级,没人超过。
3. **保守起步**:即使物理内存更大(Xiaomi 14 有 12/16G 版本,本机实际容量未确认),8 GiB 窗口必然可用;扩到满配留到有判据再说。

## 二、为什么 2GiB 限制早就该破(实锤)
1. **UEFI 早就声明了 ~11.8 GiB 高区**:`src\uefi-houji-work\Platforms\Xiaomi\houjiPkg\Include\Protocol\HoujiRootRAM.h:6-7` `HOUJI_ROOT_RAM_LOW=0x8C0000000 / HOUJI_ROOT_RAM_HIGH=0xBEA400000`(跨度 0x32A400000≈11.8 GiB);`MemoryMapLib.c:51` 把它整块 `AddMem` 为常规内存(type 7,WRITE_BACK_XN)。**固件侧无需改动**(现役 r26/r70 模板即此树构建)。
2. **限制只在我们配置**:`board.toml` `dram_size=0x80000000`+`owned_memory_size=0x80000000`;`dts/houji.dts` memory 节点 `reg=<0x08 0xc0000000 0x00 0x80000000>`。
3. **r19 卡点有现成解**:board.toml 注释"8 GiB overflowed XNU's 16-page bootstrap tables(start_first_cpu self-loop at +0x230)"——liimagination 的 `xnu-start-s-ram8g.patch` 正是修这个:把临时引导映射钳到 ≤448 MiB(`movz x6,#0x1c00,lsl #16; cmp x24,x6; csel x24,x6,x24,hi`;其注释:8 GiB 跨度的 HeadSize≈285 MiB < 448 MiB 上限)。
4. **内核 VA 配套**:liimagination `xnu-vm-kern-kmem-io-128m.patch` 把 `kmem_io` 从 1 GiB 减到 128 MiB,腾 896 MiB 内核 VA 给 kmem_data_shared_range(8 GiB 物理下需要);我们 feed 的同位置上下文逐行存在(`out\feeds\xnu-3199e8bc\osfmk\vm\vm_kern.c:3030-3033` `.kc_size=(1u<<30)`)。

## 三、变更清单(一类=内存;全部零上机准备,批准后走 CI)
1. **新补丁** `patches/xnu/houji-start-ram8g-clamp.patch`=liimagination hunk2(start.s V=P bootstrap 前插 448 MiB 钳制;**不取其 hunk1**,Aff1 已由 native-smp-secondary.patch 覆盖);来源与 sha256 记录:`work\refscan_1127\xnu-start-s-ram8g.patch`(AAACE5B7DD3290AA…),借法=纲领四③(同代机型),借用文本按 §4.9 保持逐字(适配仅限补丁头)。
2. **新补丁** `patches/xnu/houji-vm-kmem-io-128m.patch`=liimagination vm_kern.c 一行(`1u << 30`→`128u << 20`,注释注明原因);sha256 31D427C074377102…。
3. **board.toml**:`dram_size=0x80000000→0x200000000`、`owned_memory_size` 同步 `0x200000000`(注释保留 r19 教训说明+注明 WindowSize.h 上限)。
4. **dts/houji.dts**:memory 节点 `reg=<0x08 0xc0000000 0x00 0x80000000>→<0x08 0xc0000000 0x02 0x00000000>`(8 GiB;三者须一致=P5 期 CI 规则)。
5. **series**:两个补丁加进 `patches/xnu/series`(native-smp-secondary 之后,顺序无依赖);CI patchtest+第二遍链接是补丁可打可编译的最终裁判。
6. **mk74 断言**(照 mk73 模式):payload args/配置含 dram_size=0x200000000;ADT memory reg=8 GiB(扩展 work/chkadtcpu.py 或 grep);内核≠r72/r73;回归串全套;**新内核先"探路烧"一次**(P11 新规:连 2 坏即重跑 CI 换 relink)。
7. 回滚=镜像 h2(r73 收线内容)+board.toml 旧值。

## 四、风险与判据(申报,纲领 v3.3)
| 风险 | 等级 | 缓解/判据 |
|---|---|---|
| r19 引导表自环复发 | 中(正是本轮要修的) | 钳补丁直接对症;若复发=钳补丁未生效,查 series 顺序 |
| DarwinFlush(DarwinBoot Entry.S:19-31,dc civac 循环)刷 owned 窗口 | 低 | 8 GiB=4 倍刷新时间,绿条阶段预计延长 1-3 秒(推测);P11 候选 F 本就指认此循环,若坏模式率上升,这也是定位材料 |
| P11 布局敏感(新 relink 可能落坏布局) | 中 | 探路烧新规:连 2 坏→重跑 CI(问题记录 P11 13:58 条已立) |
| 高区有隐藏 carveout(TEE/调制解调器等) | 低 | MemoryWindow.h 的 excluded 机制按最终 UEFI map 自动排除非空闲段;span 又整块声明为 conventional,理论无洞;若出现奇怪崩溃,读回 grep darwinboot-memory-excluded 相关行 |
| hw.memsize 判据不可直读 | 低 | iOS 关于本机不显示 RAM;判据=①DarwinBoot 交接屏显(绿条期画面会打窗口/内存行,录像可读,参照 P11 交接屏 va/pa 行);②短会话读回的早期记录行(pmap/内存统计);③若都不足,调频轮给心跳捎带一行(成熟模式) |
| Data/seed/logfs 受影响 | 无 | 全在 UFS/打包层,与 DRAM 窗口无关(P10 机制已闭合) |

## 五、预期效果
- `hw.memsize`≈8 GiB;jetsam/压缩压力显著缓解(2 GiB 时代从未测过内存压力=盲区);GPU 轮的缓冲区前提(nian0114 在 8 GiB 机上仍遇 OutOfMemory(Device),2 GiB 必然不够);启动期 dyld 映射余量更大。
- 不承诺:流畅度(那是 GPU 轮的事);只承诺"内存不再是瓶颈"。

## 六、复评触发器
- liimagination/nian0114/lonzzi 任一仓库新增触及 start.s/vm_kern.c/MemoryMap 的提交→复扫。
- 实施后 hw.memsize 读数≠8 GiB→按 excluded 机制查 UEFI map(读回 grep)。
- 8 GiB 稳定后,若 GPU 轮需要更大窗口,另立"扩窗到 11.8 GiB"轮(上限仍受 WindowSize.h 0x200000000 限制→需先放宽该常量=官方文件改动,需单独立项)。
