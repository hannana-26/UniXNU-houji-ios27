**一句话卡点:** r20/r21 内核在 DarwinBoot 交接之后,有时没有执行到内核第一条指令(无蓝条,10 秒后绿条消失,约 58 秒后静默复位),有时执行到了却卡死(有蓝条,之后 120 秒不动、不出 panic 屏)。同一个 r20 镜像两次结果不同,所以结果不只由内核补丁决定。r19 是好的(蓝条→约 24 秒后出 initproc panic)。

## 1. 环境
- 设备:小米14 houji(SM8650),fastboot 序列号 6e0f97c8。userdata 已是 iOS 镜像(15.25GiB),**不要重刷**,不要回 HyperOS。
- 启动链:Mu-Silicium UEFI(ShengLog v4.4,`build\uefi-r19\Mu-houjif-r19.img`)→ UniXNU payload → DarwinBoot → XNU xnu-12377 → launchd。
- 设备仓库:`src\UniXNU-houji-ios27`,分支 storage,最新 commit 见文末 §7。构建只走 GitHub CI(`hannana-26/UniXNU` 的 macos.yml),本机只重打包。
- 启动方式:只 `fastboot boot <镜像>`。`$env:Path+=";D:\yizhishouji\tools\platform-tools"`。每次启动前必须用户说"开始"并确认"录像准备好了吗"。
- 屏幕标记(entry-probe 画在屏幕最上方的色条):绿条=DarwinBoot 完成 ExitBootServices;蓝条=内核第一条指令(MMU 关)已执行;品红条=stage 2(本轮没启用 --no-stage2,所以不会出现)。蓝条通常在绿条后 1 秒内出现。
- 看视频的工具(WSL 用 `/root/uvenv/bin/python3`):`work\scan20c.py <视频> <帧目录>`(每 0.5 秒统计亮度和各色像素数,蓝条≈2.3 万像素即为有)、`work\ocr4k.py <视频> <秒>...`、`work\grab.py`。本模型不能看图,靠数值和 OCR。
- 镜像与构建链:`work\mk21.sh <CI号>`(重打包 payload + entry-probe + adtfix)→ `work\mk21.py`(出 boot 镜像)。

## 3. 已排除(别再走)
1. **读取器/BootLog 窗口线**:冻结(r14–r19 六轮无产出),除非 panic 文本不足以定位。
2. **entry-probe 补丁写错**:已在 r20 内核上核对,探针安装正确,入口代码与 r50 结构一致(只是 `__TEXT_EXEC` 偏移 +0x8000;r21 入口 0xfffffff00ad83488,r50 为 ...81488,r20 为 ...85488)。
3. **"无蓝条"是 r20 补丁里的 47 位 TTBR0/16-bit ASID 引起的**:不成立——r21 去掉它们后仍有无蓝条的轮次。
4. **r20 第1次视频的绿条/蓝条是看漏**:不成立——4K 视频用像素统计,蓝条有无非常清楚(r21、r20 第1次=0 像素,r20 第2次=2.3 万像素)。
5. 加大内存、移植 BootProgress、BootLog v4/v5 漂移:已决定不做/延后(见 porting.toml diagnostics)。
6. **"r20 的卡死(有蓝条后不动)被 r21 修好了"**:**没有结论**——r21 这一轮落在无蓝条模式,没有跑到内核里面,所以 r21 对卡死问题毫无信息量。

## 4. 卡点(要新会话回答的两件事)
A. **有蓝条的轮次,r20 内核为什么在入口之后卡死、不出 panic 屏?**(r19 同阶段能出 panic 屏。嫌疑:aston bring-up 补丁里的其他部分;早期 TCR 改动目前只是"可能",待 r21 在有蓝条模式下验证。)
B. **无蓝条模式是什么?**(DarwinBoot 交接到内核第一条指令之间出问题,或每次开机状态不同。同一镜像 r20 出现过两种结果,说明与上一次开机怎么结束、UFS/TZ 状态、或内核加载位置有关。)

## 5. 下一步建议(一轮只改一类东西,每次都要用户"开始"+录像确认)
1. **原样再跑一次 r21**,同时让用户记录"这次开机前手机是怎么关的"(长按电源关机多久、是否自己重启过、是否隔了 30 秒以上才进 fastboot)。目的:A 看 r21 有蓝条时能不能出 panic 文本(pc/lr/far/esr/w);B 积累"开机前状态↔有无蓝条"对照表。
2. 若 r21 又无蓝条:用 r19 镜像(已知好的)再跑一次当对照。r19 也出现无蓝条 ⇒ 问题与内核补丁无关,在 DarwinBoot/UEFI 交接(查缓存维护、关 MMU、跳转、内核加载地址是否每次变);r19 稳定有蓝条 ⇒ 问题与 r20 的内核有关。
3. 若 r21 有蓝条并出 panic:读 pc/lr/far/esr,用 `work\sym.py`、`dis46.py` 定位 launchd 的 SIGSEGV(这才是 Stage 7 的主线)。
4. 若 r21 有蓝条仍卡死:二分 bring-up 补丁(r22 = r19 + 只 `houji-initproc-fault-panic.patch`,确认 panic 补丁自己没问题;再逐文件加回 zzzz)。
5. 反直觉的"最后一跳"(无蓝条的根因)属于 Opus;取证、重打包、对比、二分用 Sonnet。
