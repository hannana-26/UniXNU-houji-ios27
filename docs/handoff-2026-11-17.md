**一句话卡点:** r20/r21 内核在 DarwinBoot 交接之后,有时没有执行到内核第一条指令(无蓝条,10 秒后绿条消失,约 58 秒后静默复位),有时执行到了却卡死(有蓝条,之后 120 秒不动、不出 panic 屏)。同一个 r20 镜像两次结果不同,所以结果不只由内核补丁决定。r19 是好的(蓝条→约 24 秒后出 initproc panic)。

## 1. 环境
- 设备:小米14 houji(SM8650),fastboot 序列号 6e0f97c8。userdata 已是 iOS 镜像(15.25GiB),**不要重刷**,不要回 HyperOS。
- 启动链:Mu-Silicium UEFI(ShengLog v4.4,`build\uefi-r19\Mu-houjif-r19.img`)→ UniXNU payload → DarwinBoot → XNU xnu-12377 → launchd。
- 设备仓库:`src\UniXNU-houji-ios27`,分支 storage,最新 commit 见文末 §7。构建只走 GitHub CI(`hannana-26/UniXNU` 的 macos.yml),本机只重打包。
- 启动方式:只 `fastboot boot <镜像>`。`$env:Path+=";D:\yizhishouji\tools\platform-tools"`。每次启动前必须用户说"开始"并确认"录像准备好了吗"。
- 屏幕标记(entry-probe 画在屏幕最上方的色条):绿条=DarwinBoot 完成 ExitBootServices;蓝条=内核第一条指令(MMU 关)已执行;品红条=stage 2(本轮没启用 --no-stage2,所以不会出现)。蓝条通常在绿条后 1 秒内出现。
- 看视频的工具(WSL 用 `/root/uvenv/bin/python3`):`work\scan20c.py <视频> <帧目录>`(每 0.5 秒统计亮度和各色像素数,蓝条≈2.3 万像素即为有)、`work\ocr4k.py <视频> <秒>...`、`work\grab.py`。本模型不能看图,靠数值和 OCR。

## 3. 已排除(别再走)
1. **读取器/BootLog 窗口线**:冻结(r14–r19 六轮无产出),除非 panic 文本不足以定位。
2. **entry-probe 补丁写错**:已在 r20 内核上核对,探针安装正确,入口代码与 r50 结构一致(只是 `__TEXT_EXEC` 偏移 +0x8000;r21 入口 0xfffffff00ad83488,r50 为 ...81488,r20 为 ...85488)。
3. **"无蓝条"是 r20 补丁里的 47 位 TTBR0/16-bit ASID 引起的**:不成立——r21 去掉它们后仍有无蓝条的轮次。
4. **r20 第1次视频的绿条/蓝条是看漏**:不成立——4K 视频用像素统计,蓝条有无非常清楚(r21、r20 第1次=0 像素,r20 第2次=2.3 万像素)。
5. 加大内存、移植 BootProgress、BootLog v4/v5 漂移:已决定不做/延后(见 porting.toml diagnostics)。
6. **"r20 的卡死(有蓝条后不动)被 r21 修好了"**:**没有结论**——r21 这一轮落在无蓝条模式,没有跑到内核里面,所以 r21 对卡死问题毫无信息量。

## 4. 卡点(要新会话回答的两件事)
A. **有蓝条的轮次,r20 内核为什么在入口之后卡死、不出 panic 屏?**(r19 同阶段能出 panic 屏。嫌疑:aston bring-up 补丁里的其他部分;早期 TCR 改动目前只是"可能",待 r21 在有蓝条模式下验证。)
B. **无蓝条模式是什么?**(DarwinBoot 交接到内核第一条指令之间出问题,或每次开机状态不同。同一镜像 r20 出现过两种结果,说明与上一次开机怎么结束、UFS/TZ 状态、或内核加载位置有关。)

## 5. 下一步:大胆版方案(2026-11-17 午后重订,取代上一版保守二分)
**总原则变化:** 以前"一轮只改一个变量"是因为每轮只有一张照片;只要能读回内核日志,一轮就能带多个改动。所以先修"看得见",再大胆批量试。

**第 0 步(需向用户申请一次红线放宽,只读):** 当前红线只许 `fastboot boot`/刷 userdata。请用户批准额外两条**只读**动作:`fastboot reboot fastboot`(进 fastbootd)和 `fastboot fetch userdata:<偏移>:<长度> 文件`(平台工具 37.0.1 已支持 fetch;读出 userdata 尾部 32 MiB 的 sheng-log 窗口,不写任何分区)。依据:getvar 显示 is-userspace:no、当前槽 b、未刷过 vendor_boot/recovery 的原厂 `inputs\rom215\vendor_boot.img` 在手。批准后,先读出"上一次真正进了内核的那轮"(r20 第2次,有蓝条后卡 120 秒;之后三轮没进内核,窗口应未被覆盖)的日志,这一步不需要再开机。fetch 不可用就退回方案 B。头魔数在 `package/BootLog.c`;窗口几何见 porting.toml diagnostics;`work\test_shlog4.py` 可离线解码。
**方案 B(fetch 不可用):** 学 sheng 做"fastboot boot 的 Linux 读取镜像"(sheng:`package/linux-log/`、`scripts/read-sheng-log.py`,SM8550 用 ianchb 主线内核 + busybox initramfs,USB CDC 吐窗口)。SM8650 主线内核可参考 `ycrrongos/snapdragon-8gen3-linux`、`FrontMage/ubuntu-nx769j-build-ci`(红魔9 Pro,同 SoC);houji 无主线 DTS,需套 sm8650-mtp/hdk 的 DTS 做最小 UFS+USB。**绝不能用安卓原厂 init:** 它会按 fstab 的 formattable 把 userdata 当损坏卷格式化,毁掉 iOS 镜像;initramfs 必须自带 /init 且不挂载 userdata。

**第 1 步:批量对照(有日志后每轮带多个改动,不再单变量):**
- r22a(对照):r19 的内核 + `houji-initproc-fault-panic.patch`(只要 panic 屏出 pc/lr/far/esr)。
- r22b(信息版):r21 内核 + sheng 的启动检查点补丁整包 `sheng-bootstrap-checkpoints`、`zzzzzz-sheng-bsd-checkpoints`、`sheng-headless-startup-checkpoints`、`sheng-startup-failure-log`、`sheng-process-exit-log`(都在 `src\UniXNU-sheng\patches\xnu-12377\`,已是 sheng 实机在用的 series 顺序,序号见其 `series`)。目的:卡死时日志里有"走到哪一步"。
- r22c(去掉 UEFI 读取器):用 r50 时代不带读取器的 UEFI(`build\bootimg-r1\boot-houji-r50-probe.img` 里的)配 r21 payload。理由:读取器 UEFI(v4.4)在交接前读 GPT/UFS,可能让存储/TZ 状态每次不同,是"无蓝条/好坏交替"的头号嫌疑。注意 r19(好)也带读取器,所以只是嫌疑,不是结论。
- 入口色带从 2 条扩成 YX-lab 的 13 个检查点(`src\YX2748198202-lab-UniXNU-shennong\scripts\patch-entry-bands.py`,同 SoC、同 24A446 内核):三条都没出现=没进内核;只有绿=入口前出问题。同时借其两条硬规则:`pacibsp` 之后的函数体不能插跳转型 cave;`_start_first_cpu` 里 SP 与返回地址共用同一滑动换算,只改一边会双双错位。**检查我们的探针是否违反:** r20 的入口 0xfffffff00ad83488,与 YX-lab `_start_first_cpu`=0xad8305c 不同,需核对。
- 无蓝条模式的重复统计:r19、r21 各至少 3 次,每次记录"开机前怎么关的"。

**第 2 步:启动参数向 sheng 现行配置靠拢(sheng `board.toml` L185/L243,已在 SM8550 实机桌面):** 候选追加 `ml-timeout-lock-panic-scale=40`、`boot-progress=2`、`uefi-watchdog=1`(sheng 用它让 UEFI 看门狗在交接异常时复位)、`smp=1`;去掉 `cpus=1` 之前先确认 lonzzi 的 houji(iOS16,8 核)怎么处理。内存暂不加(sheng 的 `owned_memory_size` 用 4.8–6 GiB + outside-ranges 机制,需要对应新版 DarwinBoot,另立任务)。

**第 3 步:借 lonzzi 的 houji 实绩(同机型已进 iOS 16 桌面,8 核):** `src\lonzzi-houji` 的 UEFI/ADT/内存窗口(2 GiB@0x8c0000000)与我们一致,说明硬件与引导链没问题;它的日志走 logfs 分区(8 MiB FAT12,XnuLog.bin 64 KiB,头 CRC+本轮 UUID)+ OrangeFox adb。我们不刷 recovery,所以用第 0 步的 fetch 替代它的 adb 读分区。

**模型分工:** 第 0 步和 B 方案的取证/脚本用 Sonnet;如果日志里确实拿到 kernel 停止位置,"为什么停在那"的根因推理才用 Opus。
