## 1. 一句话现状

## 2. 实锤事实清单(有录像 OCR / 缓存反汇编 / 官方源码 / CI 日志依据)

- **F1 崩溃点**:libobjc `realizeClassWithoutSwift+0x30`,指令 `ldr x8,[x19]`(x19=cls 为垃圾)。r53 的 pc/lr 与缓存反汇编吻合:pc=缓存 VA 0x18041b140(该处正是 f9400268=ldr x8,[x19]),lr=0x18041b45c(上一条是 BL 到函数头 0x18041b110);panic 记录里 pc−lr=0x31c 与缓存中一致,两个独立 OCR 值保持差值 → r53 滑动值 0x2e0000 可靠(实锤)。依据:work\chk_lr.py、r53 记录。
- **F2 缓存滑动值每次启动随机**(r53=0x2e0000;r57=0x16bc000 推测,见 P2),16K 对齐。
- **F3 两次崩溃 far 的精确分解**:far = J<<34 + 0x1e6ebed30 + 该次滑动。
  - r53: J=0x120,slide=0x2e0000:0x48000000000 + 0x1e719ed30 = 0x481e719ed30(精确闭合,实锤);
  - r57: J=0xF0,slide=0x16bc000:0x3c000000000 + 0x1e857ad30 = 0x3c1e857ad30(精确闭合;slide 未确认,见 P2);
  - 即崩溃指针 = 指向**同一个**缓存类对象 A(unslid VA 0x1e6ebed30)的正确滑动指针,bit34-42 被杂位污染,bit43 以上全 0;
  - 与滑动无关的强证据:两次 far mod 16K 都 = 0x2D30 = A 在其 16K 页内的偏移(滑动 16K 对齐);
  - A 在其 16K 页(0x1e6ebc000..0x1e6ec0000)内偏移 0x2D30 → 第 3 个 4K part(part 2)。**part>0 的页必然走跨 part 的链入口解析逻辑**——崩溃对象所在页一定经过了 part 拼装路径。
- **F4 类对象 A**:位于子缓存 dyld_shared_cache_arm64e.25.dylddata(映射 0x1e6b74000 起,0x1e8d10000 止,prot RW)。A+0=isa 槽(v5 auth 条目:div=0x6ae1、addrDiv=1、keyIsData=1→ASDA、next=1),A+8=superclass 槽(div=0xb5ab、next=1,目标=A+0x28 的相邻对象)。格式与官方 slide_page_v5 吻合。依据:work\chk_target.py。
- **F5 r57 读回**(视频 build\bootimg-r10\r57rb\r57rb.mp4;逐帧 work\r57rb_dense.txt、r57rb_crop.txt):logfs 写入器正常(run 5120dfaa8…,51654B);banner 148.619s,首条 sheng-chain 209.4506s → launchd 在 kernel+60.83s 起跑,毫秒级崩溃;记录含 sheng-chain[0..40+] 与 4 条 sheng-sign。
- **F6 签名数据**:4 条 sheng-sign 的 a_key 全=0x1。原生 PAC 下这是**正常值**:官方 native-pac-keys.patch 写明内核与所有进程共用同一套硬件密钥,ml_default_jop_pid() 返回 1("must not be 0"),pager 只对 key≠0 签名。isa 绑定条目:unsignedAddr=0x2cfefc258(OCR,可能有数字误差)、key=2(ASDA)、addrDiv=1、diversity=0x6ae1,槽在 launchd 自己的页(userVA 0x100618090/0x100618130),与 chain[5]/chain[12] 的 auth+bind 条目对应。
- **F7 两条 fixup 路径不同**:dyld pager 处理 launchd 自身镜像(基址 0x100000000)的 fixup;共享缓存的 fixup 走 shared region pager(官方 native-4k-shared-region-slide.patch 的 slide_part_v5,16K 页拆 4 个 4K part)。崩溃对象 A 在共享缓存 → 走的是 **shared region pager 路径**。
- **F8 CI 实际补丁序列**(work\log-r5-full.txt 第 609-664 行):官方 native-pac-keys → native-pac-arm64-user-jop → native-4k-user-abi → native-4k-signature-hash-cache → native-4k-shared-region-slide → native-text-fixup → native-4k-block-split → darwin26-shared-region → 我们的 fileset-report-registers / source-storage / aston 两枚 → zzzz-sheng-ipados27-bringup → vmwait-dyld-pager-source-release → houji-no-ttbr0-47 → houji-initproc-fault-panic。

## 3. 未解问题台账

### P1【核心】坏类指针 bit34-42 杂位的来源 — 【2026-11-20 08:50 根因定位(推测,强证据;待 r58 实机关闭)】
- **根因**:我们自己的 houji-no-ttbr0-47.patch(r21,2026-11-17)。它关掉了 zzzz 的 T0SZ_USER=17,回落到 T0SZ_BOOT=26(BCM2837 4K + `__ARM64_PMAP_SUBPAGE_L1__`,已在打完补丁的源码树里核实,work\chk58tree.sh)→ 用户地址只有 38 位 → 用户数据指针的 PAC 签名从 bit38 开始。libobjc 的 ISA_MASK=0x7fffffffff8(保留 bit3..42;24A446 缓存 .01 里 230 处 and 立即数,work\chk_isa_mask2.py,实锤)会把 bit38..42 的 PAC 残留当作地址保留下来。
- **算术(实锤)**:far 异或(0x1e6ebed30+slide):r53=0x48000000000(bit39、42),r57=0x3c000000000(bit38-41)——杂位**只**落在 bit38..42,正好是"38 位 VA 的 PAC 起点"到"isa 掩码最高位"这一段;随启动变化=PAC 随指针/滑动变化。(台账原写"bit34-42"偏宽,准确是 bit38-42。)
- **旁证(实锤)**:zzzz 补丁原注释"arm64e user code expects pointer authentication codes above bit 46 (libobjc strips isa with a 43-bit mask), so a native 4K kernel gives user pmaps … a 47-bit range";sheng/aston 都保留 47 位,aston 进了 SpringBoard。r21 的立论"47 位 TTBR0 让入口卡死"已被 r21 自己推翻(去掉后仍无蓝条,进度记录 593-595 行),但补丁一直没撤。
- **修复**:r58 = series 去掉 houji-no-ttbr0-47(设备仓库 0750466),CI run 44648976670。
- **关闭标准**:r58 上机 launchd 过 realizeClassWithoutSwift(panic 换新地方或更远)。风险:若 r58 入口无蓝条,先按好/坏模式(同镜像多次)判断,不要立刻又归咎 47 位 TTBR0。
- 以下旧内容保留作档:
- 现象:见 F3。杂位随启动变化(0x120 / 0xF0),只在 bit34-42,bit43+ 全 0。
- 已排除(推测,较有把握):PAC 认证失败的错误码模式(应在 bit53/54 或 61/62 且铺满高位);未 fixup 的原始 v5 条目直接当指针(那样 bit63 auth 位和 bit52-62 的 next 会非 0);完整 16 位 diversity 原样残留(0x6ae1 的位形与观测不符)。
- 当前最佳假设(推测):shared region pager 的 4K part 拼装路径某处写入没清干净高位。注意:官方 slide_part_v5 本身自洽(pageOffset 以 part 缓冲区为基准、uservaddr 取 part 地址,混合后=槽的绝对用户 VA,与 Apple 16K 原语义一致);我们 zzzz 在 vm_shared_region.c 还有三处 jop 守卫改动(只影响 jop==0 的进程,已排除)——但 zzzz 对该文件的**其余改动未逐行核对**,且 zzzz 与官方 part 逻辑是否重复处理同一页未核对。

  1. zzzz-sheng-ipados27-bringup.patch 中 vm_shared_region.c / vm_shared_region_pager.c 的 hunk 与官方 native-4k-shared-region-slide.patch 逐行 diff,重点:uservaddr/pageOffset 基准、part 起点缓存(srp_part_starts)、mask、签名后的写回;
