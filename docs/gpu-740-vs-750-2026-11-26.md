# Adreno 740 → 750 差异分析与"小调整能否更好"评估(2026-11-26,零上机零代码)

证据分类:**实锤**=命令当场核实;**推测**=未读全源码/无日志;**未确认**=查不到。
抓取物:`src\ref-Adreno740`(官方,2962e28,已 unshallow)、`ref-AdrenoMetal`、`ref-AdrenoPM4`、`ref-AdrenoFirmware`、`src\nian0114-houji`(8f30445);工作目录 `work\refscan_1126\`(adreno740.md、base5c8c\=官方 5c8c1453 的 31 个对应文件)。

## 一、三个确定事实

1. **houji 的 GPU 就是 Adreno 750,不是 740**(实锤):`dts/houji.dts:15676` `qcom,chipid = <0x43051401>`、`:15677` `"Adreno750v2"`、`:15685` `compatible="qcom,adreno-gpu-gen7-9-1"`。官方 Adreno740 驱动自述 "covers A740 on SM8550",`NativeAdrenoABI.h:152` 示例 chip_id=`0x43050a01`(740)。
2. **官方自己明确说 740 驱动不能套 750**(实锤):官方 `docs/devices/nx769j-xwsjjctz.md`(红魔9 Pro,SM8650)——defconfig 把 `CONFIG_XNU_NATIVE_ADRENO` 设为 `n`,理由 "SM8550 GPU stack targets Adreno 740 while this board has Adreno 750";`meizu21` 的 GPU 状态=`planned`(A750/SM8650,DT profile 43051400/43051401)。官方仓库 167 条提交历史里 grep `750|8650|houji|pineapple` 只命中 1 条无关提交。
3. **已经有人在 houji 上把 740 驱动改到 750 并跑出桌面渲染**(实锤,代码+文档):`nian0114/UniXNU-houji`(iOS 16)。其 `docs/known-issues.md:10`:"Adreno 750 已完成真实命令提交、内存写回、完成同步和 iOS 桌面渲染,但持续交互仍会明显掉帧;打开应用可能短暂黑屏;紫色阴影/文字异常"。其 `roadmap.md:21`:"上游 sheng 为 SM8550/A740,houji 为 SM8650/A750 … 不按章节直接复制其寄存器或固件"。

## 二、740 与 750 的差异(分三层)

### A. GPU 型号表差异(来源 Mesa `freedreno_devices.py`,权威公开表,实锤)
| 项 | A740(0x43050a01) | A750(0x43051401) |
|---|---|---|
| 子代模板 | `a7xx_gen2` | `a7xx_gen3`(+ `QCTDD10789828`、`has_independent_icache_miss`) |
| GMEM | 3 MiB | 3 MiB(同) |
| CCU/tile 对齐/tile 最大 | 6 / 96×32 / 2016×2032 | 同 |
| highest_bank_bit | 16 | 16(同) |
| 魔术寄存器表 | a740_raw_magic_regs | **自己一套**(例:`UCHE_CACHE_WAYS=0`、`SP_CHICKEN_BITS=0x10000400`、`SP_CHICKEN_BITS_2=0x00431800`、`SP_CHICKEN_BITS_3=0x00800000`、`PC_MODE_CNTL=0x3f1f`、`UCHE_UNKNOWN_0E12=0x40000000`、`RB_CCU_DBG_ECO_CNTL=0x02082000` 等) |
结论:**架构规格(GMEM/CCU/tile)一样,差在"一批初始化寄存器值"和少数硬件 quirk**。Linux 对应 gen7_9_1(houji.dts 的 compatible)。

### B. 官方 Adreno740 驱动里"A740 专属"的部分(实锤:grep 全库)
官方驱动 72 个源文件/约 11,900 行,其中**真正写死 A740 的只有**:
- `NativeAdrenoA740HwInit.h`(169 行,**脚本生成**,自述 "derived from a6xx.xml … a6xx_catalog.c (a740_hwcg, a730_protect)"):A740 的寄存器偏移、HWCG 表(54 项)、CP_PROTECT 表(46 项)。
- `NativeAdrenoPwrupRegs.h`(16 个寄存器,"Generated by derive-a740-pwrup.py")。
- `NativeAdrenoService.cpp`:`SHENG_GMU_*` 常量(sheng 的 GMU 固件字节数/sha256、Command DB 基址 `SHENG_GMU_COMMAND_DB_BASE`、`SHENG_GMU_VOTES_CHIP_ID`、`SHENG_GMU_CORE_GPU_DELTA=0x6a000`)——**这些是平板 sheng 的板级数据**。
- 固件名:`a740_sqe.fw`(SQE 微码)、GMU 固件 `sheng_gmu_firmware`(都要换成 750 的:`a750_sqe.fw`、`a750_gmu.bin`)。
- 其余(Vm/Memory/Submit/Ring/Client/UserClient/Irq/Timer/Sha256…约 9 成)**与型号无关**,是通用的 SMMU 页表/BO/提交/fence 逻辑。

→ 所以"只改版本号"**不成立**,但"改的面其实不大":改**三块数据表**(HwInit、Pwrup、板级常量)+**换固件**,逻辑代码基本不动。**这是推测**:我没逐行验证 750 的寄存器偏移是否和 740 一致(gen7_2 与 gen7_9_1 的 GMU/RSC 布局可能不同,Linux 里它们是两个独立 catalog 条目)。

### C. nian0114 实际改了什么(实锤:对他自己钉的基线 5c8c1453 做 numstat)
他的基线是官方 `5c8c1453`(和他拷贝最接近,10/23 文件逐字相同)。他**只取了官方 31 个文件**,另外 65 个(共约 7,200 行,含全部 tests)没用:
- **没用的恰是 A740 专属物**:`NativeAdrenoService.cpp`(637 行,sheng GMU 板级)、`NativeAdrenoA740HwInit.h`、`NativeAdrenoRing.cpp`、`NativeAdrenoGpu*.cpp`、`GmuContext/GmuMemory/GmuService/SmmuService/Irq/Client`、`Pwrup*` 等——即**官方负责"开机上电 GMU/CP"的整条路径他全部没用**。
- **取而代之的是自己写的 750 硬件自举**(约 67 个文件/9,800 行):`Gpu*`、`Gmu*`(GmuExternalCanary、GmuInternalExec、GmuHeldTcm)、`Hfi*`、`GpuGen7Table.h`("Register facts: OnePlus graphics-kernel 453d8875, gen7_9_1; generated")、`HoujiGpuNativeProvider.inc`(`gHoujiDeviceInfo={0x43051401u,3u<<20,…}`)、vendor/`Ace5Gmu`(一加 Ace5 同 SM8650 的 GMU/HFI)。
- **只拿了官方的"通用后端"31 个文件**并改造(Publish +588/-113、Memory +178/-135、Vm +128/-180、UserClient、Submit、Cpu…):为适配 iOS 16 和 houji 的 CPU 16K/GPU 4K 页、他的 128 段批量提交(method 17)、4096 对象容量、WC 池等。
- **ABI 他改成 version=1、maxBuffers=16 + SubmitBatch(method 17)**,而官方是 version=2、maxBuffers=128,**且官方新增优先级调用占用的正是 method 17**——两边 ABI 已分叉(nian0114 自己在 upstream-features.md 记了:"Adreno740 的多 ring 抢占不能直接覆盖:上游新增优先级调用占用 method 17")。

## 三、"小调整能不能比目前预期更好?"(诚实评估)

**目前预期成果**(交接文档/porting.toml):GPU 轮=从零做 Metal/Adreno 750,"完全没有开始",无现成东西。

**小调整路线的结论:有明显好处,但不是"改个版本号"那么轻,而且有四个必须先过的坎。**

好处(有依据):
- 官方 740 的**通用后端**(SMMU 页表、BO、提交、fence、抢占调度、诊断)已在 sheng 真机验证过命令提交与扫描输出(官方 README 自述:"GPU commands and scanout copy have been verified on sheng"),比从零写省掉最大块工作量。
- nian0114 已证明 **750 自举 + 这套后端可以在 houji 上出桌面**(iOS 16,同一 SoC 同一设备)。他的 750 自举代码(Gen7 寄存器表、GMU、HFI)是现成可借的硬件层。
- 所以"预期"可以从"从零做"**上调为"借 nian0114 的 750 自举 + 官方通用后端"**,工作量估计大幅下降(推测,无工时依据)。

四个坎(都是未确认/风险):
1. **iOS 16 → iOS 27**:nian0114 的是 iOS 16.7.16(Darwin 22/23);我们是 24A446(Darwin 25)。内核 ABI、IOKit、Metal 用户态链都不同。他的 `AdrenoMetal` iOS 16 补丁(`adrenometal-ios16*.patch`)对 iOS 27 不适用。官方 AdrenoMetal 有 `--target ios27` 但 #315(外部 PR,未合并)才让它编译通过,**且无上机验证**。
2. **官方 740 与 nian0114 分叉**:ABI 版本、method 17 冲突。我们应以**官方当前主线为底**(因为我们要跟 iOS 27 的官方 AdrenoMetal 配对),再把 nian0114 的"750 自举"以**数据表+探针**形式嫁接,而不是拿他的整套 31 个改造文件(那些改造绑定 iOS 16 与他的批量提交方案)。
3. **许可/来源**:nian0114 的 750 自举大量引用 Ace5(`BSD-2-Clause-Patent`,可借)与 Qualcomm/OnePlus 内核寄存器事实;GMU/ZAP 固件需要 houji 设备自己的固件(我们走 userdata,固件文件从哪里取=**未确认**)。
4. **效果天花板**:即使全部接上,nian0114 自己写明仍"持续交互明显掉帧、紫色/文字异常"。**所以"达成效果比预期好"只对"能不能出 GPU 渲染"成立,对"体验流畅"不成立**,别在这一步承诺性能。

## 四、对 #310/#315/#305 的处置(落实 11-26 上午的核实)
- **#310(已合并)**:ABI 守卫规则可直接抄进 mk 脚本断言——对 `NativeAdrenoABI.h` 取 sha256,与内核 json 的 `adreno_abi_sha256` 对比。**GPU 轮才用,现在不动。**
- **#315 / AdrenoMetal#71**:外部人员、未合并、仅"让 ios27 能编译",是编译开关,不是适配;**仅作 iOS 27 编译注意事项**。
- **#305**:Turnip 失败根因的诊断保留,与我们 logfs"只收 printf"问题**不是同一回事**,暂不解决读回通道。

## 五、建议(待用户批准;顺序与用户 11-26 决定一致:**先触摸**)
1. **触摸轮**照旧先做(第 0 步零上机核对 UEFI 触摸上电)。
2. GPU 轮前置准备(零上机,可与触摸并行,不占用"一轮只改一类"):
   - a) 通读 nian0114 `GpuGen7Table.h`、`HoujiGpuNativeProvider.inc`、`GpuPowerOnlyHandoff.h`,列出"750 自举最小集";
   - b) 对照 Mesa/Linux gen7_9_1 与官方 `NativeAdrenoA740HwInit.h` 逐寄存器核对偏移是否一致(升级"推测"为"实锤");
   - c) 确认固件来源(houji 的 `a750_sqe.fw`/`a750_gmu.bin`/zap)。
3. GPU 轮立项时,按"官方通用后端为底 + 750 自举数据表嫁接 + 以 #310 守卫配对 AdrenoMetal"设计;不采用 nian0114 的 iOS 16 整套改造。
