## 一、本轮新发现(改变排序的关键)

**我们的内核现在只开了 1 个 CPU 核心**:`src\UniXNU-houji-ios27\board.toml:96` 的 kernel_args 里是 `cpus=1`,porting.toml cpu 区 limits="只验证单核;副核上线与频率管理未开始"(实锤)。
- houji 有 8 个核(houji.dts:472-642,cpu@0..cpu@700,PSCI 启动,实锤)。**目前跑 iOS 27 的只有第 0 号核=最弱的 A520 小核**(lonzzi 实测 MIDR 410fd801=A520,CPU0 约 1.69GHz,实锤,lonzzi archive\docs\cpu-scheduling.md)。
- 之前"点什么都慢"全部归因于"无 GPU"——**不完整**。无 GPU 的 CPU 复制渲染是在**唯一一颗小核**上同时跑 SpringBoard、backboardd、触摸、存储、复制画面。这是第二个原因,而且修起来比 GPU 便宜得多。
- 同设备先例(实锤,同一手机 houji,iOS16):lonzzi r55 八核预检通过(`HOUJI SMP PREFLIGHT: PASS; 8 cores`),**r56 用户确认"全屏设置列表滚动明显改善"**(同一份文档);其后另加 CPU 调频(r195)用户仍报"响应只有小幅提升"——所以多核是大头,调频是小头。
- 官方同 SoC 先例:aston(SM8550,进了 SpringBoard)args 带 `smp=1 armcpu-spi-ipi=1 armcpu-self-ipi=1 armcpu-edge=1 sheng-cpufreq=4`(aston\board.toml);fuxi 带 `sheng-smp=1 sheng-cpufreq=4`(实锤)。我们的 ArmCpu 组件已经在 board.toml components 里(实锤),**组件不用新增,主要是改参数+核对 ADT 里有没有 8 个 CPU 节点(未确认)**。
- **GPU 反过来也依赖多核**(推测):Turnip/提交线程/中断处理都要 CPU 时间,单小核上即使有 GPU 也会被卡住。nian0114 有 GPU 仍掉帧,他是 8 核+调频+批量提交一起上的。

## 二、给用户的大白话结论

1. 背光不该排前面,你说得对。它的代码已经在内核里了,验证只要"进设置拖一下亮度条+读回心跳",**不单独占一轮**,哪次上机顺手做。唯一提醒:固件初始亮度只有最大值的约 11%(0x133=307/0xb32=2866,背光第0步文档),户外会偏暗,但这是"体验",不是"流畅"。
2. **最高性价比=先把另外 7 个核打开**(改参数为主,不用写大驱动,有同设备实机先例)。它同时是 GPU 的前提。
3. GPU 仍是"质变点",但它是 4-6 轮的大工程,且 nian0114 做完仍掉帧——**放第二,不是不做**。GPU 前置三项零上机核对照常做,不占轮。
4. 睡眠/电池/Wi-Fi/音频都推后,理由见表。

## 四、为什么不是"GPU 直接第一"

1. 成本差 5~10 倍:多核轮预计 1-2 轮、主要是参数;GPU 至少 4-6 轮,固件来源还没确认。
2. 收益可叠加:多核让**现在**每次上机操作就变顺手,也让后面 GPU 每轮验证更快、更不容易被慢误判。
3. 风险对冲:GPU 轮每轮都要上机,多核先行等于给 GPU 铺了跑道。
4. 用户的"GPU 优先"指令仍成立:GPU 前置三项继续做(零上机),GPU 是第 3 序而非被取消。**是否改序由用户决定**。

## 九、本轮新发现(两条,改变排序)

### 发现 A:八核的"软件部分"可能已经在我们的内核里
- 官方补丁 `native-smp-secondary.patch`(处理 SM8550 的核号放在 MPIDR Aff1:`and x0,x15,#0xFFFF`)**已在我们 CI 的补丁序列中**(实锤:work\log-r5-full.txt 有 `== kernel: patch native-smp-secondary.patch`)。官方 ArmCpu 也已有 `smp=1 / armcpu-spi-ipi / armcpu-self-ipi / smp-gic`(官方 ArmCpu.cpp:279/334/511/514,实锤)。
- houji.dts 的 GIC 重分发器步长 0x40000(houji.dts:1493,实锤),官方 ArmCpu 认 0x20000/0x30000/0x40000(实锤)。lonzzi 另提醒"通用代码默认 0x20000,首核启动不会检验这个差异"——**已有 DT 属性可读,属低风险,但需上机验证(推测)**。
- 所以多核轮预计**只改 board.toml 参数**(smp=1 armcpu-spi-ipi=1 armcpu-self-ipi=1,cpus=8)+ ADT 的 8 个 CPU 节点核对(未确认)。
- **副核 PAC 密钥(11:15 已核实,风险解除,实锤)**:官方 `native-pac-keys.patch`(xnu-12377,我们的 CI 序列已含)的 `PAC_INIT_KEY_STATE` 宏写明:首个核用 splitmix64 生成密钥并存入 `native_pac_keys`,**之后每个核(含热复位)进入时都从内存读同一套**写入 APIA/APIB/APDA/APDB/APGA 寄存器,且此时 MMU 关闭保证副核读到(patch 第 150-195 行)。所以 liimagination 的 ArmCpu 里那个 `syncPacKeysToMemory` 是他们 ArmCpu 自己的实现,不代表官方缺这块。本条先前写的『必须先查』作废。**仍未确认**:官方 ArmCpu 在副核走的路径是否会经过这个宏(多半是,因为副核走 reset vector→start.s;上机读回可证)。

### 发现 B:我们只用了 2 GiB 内存
- houji.dts 的 memory 节点=`0x8 0xc0000000 / 0x80000000`(2 GiB,实锤);board.toml `dram_size=0x80000000`、`owned_memory_size=0x80000000`。
- 当初限 2GiB 的原因(实锤,进度记录 r19 与 board.toml 注释):8GiB 会溢出 XNU 的 16 页引导页表,start_first_cpu 自环。
- **liimagination 的 `xnu-start-s-ram8g.patch`(约 20 行)正是修这个问题**:把临时引导映射钳在 448MiB(`movz x6,#0x1c00,lsl #16; cmp x24,x6; csel`);另有 `xnu-vm-kern-kmem-io-128m.patch`(kmem_io 1GiB→128MiB,腾出内核虚拟地址)。他们 8GiB 机器已稳定进桌面(Boot 48/69)。
- houji 上 8GiB 高区 lonzzi 已实测:r35"8 GiB window"装载器测试通过、高区探针地址转换 WB 正确(lonzzi archive\docs\bringup.md:94/:876,实锤);注意其 L882 自己写明"这只证明内存/存储传输,不是 8GiB iOS 用户态稳定性"。
- **为什么重要(推测,待证)**:iOS 27 + SpringBoard + CPU 复制渲染在 2GiB 里运行,内存压力(jetsam/压缩)很可能是"慢"的第三个原因;而 GPU 轮要给 GPU 缓冲区分大块内存,2GiB 基本不够(nian0114 在 8GiB 机上还遇到 `OutOfMemory(Device)`,窗口另需扩大)。**我们的记录里从没有人测过内存压力,这是盲区。**
