## 一、核心结论(三句话版)

1. **实锤:我们现役烧进手机的固件(Mu-houjif-r26.img,r55–r69 全系模板)里没有任何触摸上电代码**——触摸芯片 S3910 的供电(ldob9 3.0V/ldob12 1.8V)和三路 QUP 时钟没人申请,进内核后 SPI 总线大概率是死的。
2. **实锤:但干这活需要的三个"协议司机"(CmdDbDxe/RpmhDxe/ClockDxe)已经在固件里**,lonzzi 那 78 行上电函数(TouchHandoff.h)可以原样移植进来——固件上电轮是小改动,不是从零造。
3. **按交接文档 §四 的决策树,触摸轮正式拆成两轮(各一类,均待用户批准):固件上电轮 → 内核驱动轮。**

## 二、任务①:我们的启动链是否调用 PrepareTouchHandoff?——**不调用(实锤,三重证据)**

### 证据 A:烧机固件二进制解剖(最硬的一条)
对象 = `build\uefi-r26\Mu-houjif-r26.img`——`work\mk69.py:3` 实锤它就是 r69(r55–r69 全系)打包用的 UEFI 模板。
方法:`work\step0_uefi_strings.py`(新建,复用 lzmapeek.py 的解压原理)把 ANDROID bootimg 的内核段解 gzip→解 LZMA FV(解出 7,692,296 字节),对原始段+解压结果搜 ASCII 和 UTF-16LE 两种编码的字符串:

| 探针串 | 含义 | 命中 |
|---|---|---|
| `HOUJI TOUCH UEFI` | TouchHandoff.h 每步成功的 Print 字面量(build\uefi-r3\...\TouchHandoff.h:25/31/37 等 8 处) | **0** |
| `houji_touch` / `houji_touch_probe` | 上电成功才追加的内核参数串 | **0** |
| `houji-touch-vdd` | PrepareTouchHandoff 创建的 RPMh 客户名(TouchHandoff.h:51) | **0** |
| `HoujiStorageProbe` | 含上电代码的整个程序的模块名 | **0** |
| `SHLOG001` / `UniXNU`(阳性对照) | 解压有效性证明 | 1+1 / 21+8 ✓ |
| `RpmhDxe` / `CmdDbDxe` / `ClockDxe` | 三个协议驱动的模块名 | 各 u16=1 ✓(在!) |
| `gcc_qupv3_wrap1_s4_clk` | ClockDxe 时钟名表条目 | u16=2 ✓(在!) |
| `ldob9` | CmdDb/稳压器名表 | u16=8 ✓(在!) |

解读:**"做事的代码"零命中,"基础设施"全部命中** → 固件里有能查稳压器地址、能发 RPMh 请求、能开关时钟的司机,但没有任何一段代码叫他们来给触摸上电。工具与输出已存:`work\step0_uefi_strings.py`。

### 证据 B:源码层,我们两个 UEFI 树的 FDF 都没把 HoujiStorageProbe 装进固件
- `build\uefi-r3\pkg\houjifPkg\houjif.dsc:122` 编译了 HoujiStorageProbe.inf(编译≠装箱);但全树 grep `StorageProbe` 在**任何 .fdf/.inc 里零命中** → 不进 FV(与证据 A 吻合)。
- WSL 实际构建树 `/root/uefi-asm`(Mu-Silicium 布局)同样:`Platforms/Xiaomi/houjifPkg/houjif.fdf` 与 `Include/*.inc` 无 HoujiStorageProbe 引用(实锤,当场 grep)。
- 我们固件真正装箱的引导主体 = `UniXNUPkg/Application/UniXNU/UniXNU.inf` + `UniXNUPkg/Driver/UniXNUDxe`(`Platforms/Xiaomi/houjifPkg/Include/DXE.inc:111-113`,r3 快照与 WSL 树一致)→ 菜单 app 直接引导 payload,不走 lonzzi 那套存储探针 app。

### 证据 C:lonzzi 自己的调用路径也证明"不借用就无法到达"
`HoujiStorageProbe.c:1056-1064`(lonzzi/我们树副本同文):`PrepareTouchHandoff()` 包在 `if (mLogFsTestRun && ...)` + `if (mXnuUfsRun && ...)` 两层开关里——它是 lonzzi **诊断存储探针 app** 内部、启动其 XNU 之前的一步。lonzzi 的 UEFI 主程序就是 HoujiStorageProbe;我们的主程序是 UniXNU 菜单,这条路径从未执行。成功后才拼 `houji_touch=1` 进内核参数(`HoujiStorageProbe.c:885-889`)。

> 三重证据互相独立、指向一致:**现役启动链不给触摸上电。P15 的"未确认"升格为实锤否定。**

## 六、任务④:houji 版 TouchProbe 设计(两轮拆分,均待用户批准)

### 第 1 轮:固件上电轮(UEFI 改动,一类;需用户批准+"开始"烧 boot 前的确认)
**改动 = 把 TouchHandoff.h 的 78 行移植进我们的引导 app,一处调用。**
1. 源:`build\uefi-r3\pkg\houjifPkg\Application\HoujiStorageProbe\TouchHandoff.h`(与 lonzzi sha256 相同 a4bae3c3…d82e,BSD-2-Clause-Patent,Ace5 派生)——原样带走,含全部 `HOUJI TOUCH UEFI:` Print 行(屏上可见,故障时人眼可判)。
2. 挂点:WSL 树 `/root/uefi-asm/Platforms/Xiaomi/UniXNUPkg/Application/UniXNU/UniXNU.c`(菜单 app,DXE.inc:112 装箱),在启动 payload 之前调用一次 `PrepareTouchHandoff()`;协议 GUID 与 `OemServices.inc` 的 mProvidesRpmhDxe/mCmdDb 一致(gEfiClockProtocolGuid 已有外部声明先例 HoujiStorageProbe.c:33)。
3. 失败策略(提议,待批):**打印结果后继续 boot**(不学 lonzzi 的 stop-and-recovery)——固件屏上留一行 `preparation=%r; enabled=%u`,同时内核侧 TouchProbe 的 printf stage/error 计数会显示 SPI 读到什么,一次 boot 同时拿到两侧证据;lonzzi 选择 stop 是因为他们只有那一侧仪器。
4. 固件纪律:构建照旧 `build_uefi.py -d houjif`(WSL 树当场钉版:记 git 状态/哈希,沿用 verifyboot/uefiid/lzmapeek 三道校验);**新模板必须过新断言**:模板解压串含 `HOUJI TOUCH UEFI` + `houji-touch-vdd`(用 step0_uefi_strings.py 改造);mkNN.sh 加"模板 sha256==新模板"断言。
5. 验收判据:boot 时屏上出现 `HOUJI TOUCH UEFI: ... firmware handoff ready`;若出现 `EFI_UNSUPPORTED/NOT_READY` = giulia 二进制协议版本/资源校验不过,按打印定位(这是设计内失败模式,无害)。
6. 风险:①RPMh HLOS client 2 与 CmdDb 版本校验(0x10001/0x10000,TouchHandoff.h:32)在我们 Binaries/giulia 预编译驱动上是否通过=未确认,失败可读;②上电后内核轮到来之前这段窗口电压是否维持=lonzzi 同款"votes retained"策略(TouchHandoff.h:75-76 不释放),与 lonzzi 一致。

### 第 2 轮:内核驱动轮(CI+上机,一类;需用户批准+每 boot"开始")
**改动 = 删 7 个替身 + 新增 package/TouchProbe.cpp(houji 版)+ builder/args 三处小接线。**
1. **协议层逐字取 lonzzi**:`HoujiTouchGpio.h`/`HoujiTouchWire.h`/`HoujiTouchReport.h`/`HoujiTouchDescriptor.h` 4 个零依赖纯 C 头文件直接放进 package/(保留 SPDX 头);引脚表/SE 基址与 houji.dts 一致,零修改。
2. **外壳取 sheng**:阶段机+`kernel_thread_start`+`mapRegion`(IOMemoryDescriptor)诊断行缓冲+发布 seqlock;**每阶段 stage/error/frames 计数全部 printf**(logfs 只收 printf 流,交接 §三.5 教训),沿用 lonzzi 的计数名(stage/error/frames/events/irqPolls/deviceMaxWrite/hostWrite/configBytes/discarded)。
3. **替换点清单**(设计内明确,不臆造):
   - `sweet_hid_touch(id,down,x,y)` → sheng 式 publish(seq++/dmb/count/xs/ys/ids/seq++/sink 回调),12 槽;
   - `IOLog` → `printf`(logfs 可读);
   - `htWait`(assert_wait_deadline/thread_block)→ `IOSleep(ms)`(内核线程内语义等价,少一层依赖);
   - `mapPhys` → sheng `mapRegion` 包装;
   - 启动门:lonzzi 的 `PE_parse_boot_argn("houji_touch")` → 我们的 `offline-touch=1`(命名跟 offline-hid-* 家族);NativeHidInput 侧 `sheng-touch-hid=1`(或带上游 2 提交后 `touch-hid=1`);
   - 消费侧归一化常数 30480/20320 → 1200/2670(NativeHidInput.cpp:296,touchSend 内);
   - 复位/初始化时序、写长度 min(设备,515)、默认描述符(不装自定义配置)、kind 白名单、3 错退出+恢复引脚——**全部照抄 lonzzi 已踩平的坑**(参考源扫描 §三.5)。
4. **Y 方向待上机判**:lonzzi/gt_decode 无镜像;sheng 因面板照片镜像过 Y。houji 首轮发布原始 Y(0..2669)+ extent 计数(`native_touch_extent`,sheng 外壳自带),读回/实际操作若上下颠倒→ publish 处加 `2669-y` 镜像(调参不算新轮)。
5. **芯片身份校验保留**:msg 里 "S3910" + build 4323384(HoujiTouchDriver.inc:115-118);我们设备若 build 不同→读回 error=141+打印实测 build,再决定放行策略(设计内可判)。
6. **ADT 不动**(P12 已证 ADT 无触摸节点;lonzzi 实机证明不需要——内核直接 mapPhys TLMM GPIO + 轮询 IRQ GPIO 寄存器,无中断、无 ADT 依赖;"不需要 ADT 节点"在读完驱动后从推测升级为**高置信推测**,上机实锤后才写实锤)。
7. 迭代预期:lonzzi 走了 5 个镜像(r48 只读探测→r49 识别芯片→r50 写长度→r51 大帧→r52 默认描述符成功);我们读回通道更全(printf 进 logfs),但**同样要多轮**,不许一轮赌全部。
8. 顺序纪律:先固件轮后内核轮(不插队合并);固件轮上机一次先定触摸供电是否成功,内核轮的全部 stage 计数才有意义。

### 不做/不在本轮
- 不做 ADT 触摸节点、不接触摸中断进内核、不动 sheng 的 Novatek 协议层(GeniSpi/Nvt* 全不借)、不动显示/背光、不碰 GPU 前置三项(留 GPU 轮立项)。
